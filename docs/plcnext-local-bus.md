# Локальная шина PLCnext

Отдельный процесс `ptusa_main` поддерживает локальные модули AXC F 2152
и AXC F 3152. Одна сборка для выбранной архитектуры содержит два транспорта:
`LIBRARY` через сабмодуль `plcnext-io-drivers-cpp` и `IOCTL` через собственный
`axio_ioctl_driver`. Транспорт выбирается типом узла в `main.io.lua`:

| Контроллер | LIBRARY, прежний тип | IOCTL, новый тип |
|------------|---------------------|-----------------|
| AXC F 2152 | `ntype = 202` | `ntype = 204` |
| AXC F 3152 | `ntype = 203` | `ntype = 205` |

Узлы AXL F BK ETH / NET2 (`ntype = 200`) продолжают
работать по Modbus и могут использоваться одновременно с локальной шиной.

## Сборка и установка

Инициализируйте сабмодуль и выберите существующий CMake preset с SDK нужного
контроллера:

```powershell
git submodule update --init plcnext-io-drivers-cpp
cmake --preset <preset-с-SDK-AXCF2152-или-AXCF3152> -DPTUSA_WITH_AXIOBUS=ON
cmake --build --preset <тот-же-preset> --target ptusa_main
```

Для ARM используется `lib/shared/arm/libAxiobus.so.11.2`, для x64 —
`lib/shared/x64/libAxiobus.so.11.2`. Сборка копирует библиотеку рядом с
исполняемым файлом под её SONAME `libAxiobus.so.11`. Установка также помещает
её в каталог `bin` соответствующей версии контроллера. Сохраняйте эту
библиотеку рядом с ptusa_main при переносе программы.

IOCTL открывает `/dev/axio_xfer0` и выполняет MXI/PDI, диагностику и обмен
процессными данными системными вызовами `ioctl`. Сборка содержит также
библиотечный транспорт, поэтому `libAxiobus.so.11` требуется рядом с
программой при любом типе узла. Параметр `PTUSA_AXIOBUS_BACKEND` удалён;
сохранённое значение в старом каталоге сборки больше не выбирает транспорт.

Для сравнения на AXC F 2152 используйте один исполняемый файл и один проект:

```lua
-- В описании локального узла main.io.lua:
ntype = 202, -- AXC F 2152, LIBRARY
-- Для следующего запуска замените строку на:
-- ntype = 204, -- AXC F 2152, IOCTL
```

Остановите процесс, измените тип и запустите его снова. Состав `modules`,
адреса и размеры буферов сохраняются. Для AXC F 3152 переключайте `203/205`.
В EasyEPLANner новым типам соответствуют `AXC F 2152 (IOCTL)` и
`AXC F 3152 (IOCTL)` в `sys_io_nodes.lua`; выбор этих типов сохраняет
`204/205` при генерации `main.io.lua`. Старые названия сохраняют `202/203`.
Оба транспорта используют одну физическую шину: описывайте один локальный
узел с модулями. Одновременные узлы LIBRARY и IOCTL блокируют обмен.
Драйвер создаётся при первом обмене с непустым локальным узлом; ошибки
выбранного транспорта не переключают программу на другой автоматически.

IOCTL пока требует проверки на оборудовании. Протокол восстановлен по ABI
`axio_xfer.h` и библиотеке 11.2; совместимость конкретной прошивки необходимо
подтвердить. Кросс-сборка и подменный транспорт аппаратную проверку не заменяют.

На этих SDK опция включена по умолчанию; `-DPTUSA_WITH_AXIOBUS=OFF` позволяет
собрать прежний вариант без драйвера. Для Windows и обычного Linux опция
выключена. Обнаруженный локальный узел с данными в такой сборке сообщает об
отсутствии драйвера и не выполняет запись.

Библиотечный драйвер работает в `Axiobus::DIRECT`, `Axiobus::EXPLICIT`;
IOCTL выполняет соответствующий явный обмен напрямую. Программа должна
иметь доступ к аппаратному драйверу локальной шины и владеть им. Не запускайте
её одновременно с другой программой, управляющей той же шиной. Компонент
`PtusaPLCnextEngineer` не подключает прямой драйвер.

На проверенном AXC F 2152 устройство `/dev/axio_xfer0` принадлежит
`plcnext_firmware` с правами `0600`. Пользователь `admin` не может открыть
его, даже если входит в группу `plcnext_firmware`. В этом случае используется
штатный wrapper, разрешённый в sudoers контроллера:

```sh
cd /opt/main
sudo /usr/bin/gdbserver-start-program-wrapper.sh \
    /opt/ptusamain/ptusa_main main.plua
```

Wrapper запускает программу от `plcnext_firmware`. Для диагностического
чтения можно добавить `--read_only_io`: основной цикл не записывает DO/AO.
При этом Axiobus всё равно инициализирует и запускает аппаратную шину,
поэтому такой запуск требует подготовленного оборудования. Ошибку доступа
к устройству нельзя устранять изменением адресов каналов.

Только для LIBRARY: если библиотека уже запускалась от `admin`, файл синхронизации
`/tmp/axiopdi` может остаться с владельцем `admin` и правами `0600`.
У существующего файла должен быть доступ на чтение и запись для пользователя
нового процесса. На проверенном устройстве с группой файла `plcnext`
владелец `admin` исправил доступ командой `chmod 660 /tmp/axiopdi`.
Исправление выполняется при остановленных программах, использующих Axiobus.
Адаптер проверяет доступ до инициализации библиотеки: иначе библиотека может
бесконечно повторять попытку открытия файла с ошибкой `EACCES`.
IOCTL не использует `/tmp/axiopdi`. Он ставит неблокирующую `flock` на
устройство, защищая от второго экземпляра этого же адаптера. Библиотека
и штатная среда PLCnext эту блокировку не соблюдают; она не разрешает
совместное управление шиной.

## Автозапуск и рабочий каталог

Для контроллеров с SysV init и systemd предназначен скрипт
[`tools/setup-ptusa-autostart.sh`](../tools/setup-ptusa-autostart.sh).
Тип служб определяется по работающей системе, а не по номеру прошивки.
PLCnext перешёл на systemd начиная с прошивки 2025.0; на прошивке 2026
служба штатного runtime называется `plcnext.service`.
Старый установщик, требующий `/etc/init.d/plcnext`, на такой прошивке выдаёт
ошибку «Не найдена служба SysV PLCnext» — замените его актуальным скриптом.
По умолчанию файлы располагаются так:

| Каталог | Содержимое |
|---------|------------|
| `/opt/ptusamain` | `ptusa_main`, `libAxiobus.so.11`, `setup-ptusa-autostart.sh` |
| `/opt/main` | `main.plua`, остальные Lua-скрипты, каталоги модулей, `ptusa_main.ini`, рабочие данные |

Поместите программу `ptusa_main`, библиотеку `libAxiobus.so.11` и установщик
`setup-ptusa-autostart.sh` в один каталог. При необходимости положите туда же
`ptusa_main.ini`. Выполните из этого каталога от `root`:

```sh
sh ./setup-ptusa-autostart.sh install
```

Установщик создаёт отсутствующие `/opt/ptusamain` и `/opt/main` с владельцем
`admin`, группой `plcnext` и правами `775` (`rwxrwxr-x`). Программа, библиотека
и установщик копируются из каталога скрипта в `/opt/ptusamain`; новые версии
заменяют существующие после остановки службы ptusa_main. Если библиотека
не поставляется с обновлением, используется уже установленная.
При запуске установщика из `/opt/ptusamain` файлы не копируются сами в себя.
INI копируется в `/opt/main/ptusa_main.ini` только при его отсутствии;
существующие настройки сохраняются.

Скрипты проекта загрузите в `/opt/main` до первого запуска программы.
Установка допускает отсутствие `main.plua`; команды `check` и `start`
проверяют его наличие:

```sh
sh /opt/ptusamain/setup-ptusa-autostart.sh check
```

Установка останавливает работающий PLCnext и управляемую службу ptusa_main,
назначает группе `plcnext` чтение файлов программы и чтение/запись файлов
рабочего каталога, исправляет владельца и права `/dev/axio_xfer0` и
существующего `/tmp/axiopdi`.
Владельцы существующих каталогов и файлов проекта сохраняются;
символические ссылки внутри проекта не обходятся.
Файл синхронизации Axiobus не удаляется.

Служба запускает `/opt/ptusamain/ptusa_main` от
`plcnext_firmware:plcnext` с рабочим каталогом `/opt/main` и повторяет
подготовку прав при каждом старте. Относительные пути к Lua-скриптам,
модулям и рабочим данным отсчитываются от `/opt/main`. Библиотека Axiobus
загружается рядом с исполняемым файлом благодаря `$ORIGIN` в RPATH.
При переходе со старой установки остановка выполняется установленной
версией службы, которая знает прежний путь программы. Запуск блокируется,
если старый экземпляр из `/opt/main` продолжает работать вне службы.
На SysV устанавливается `/etc/init.d/ptusa_main`; для регистрации используется
`update-rc.d ptusa_main defaults 99 01`, а для отключения автозапуска штатного
runtime — `update-rc.d plcnext disable`.
На systemd устанавливается `/etc/systemd/system/ptusa_main.service`, который
использует `/usr/libexec/ptusa_main-autostart` как вспомогательный скрипт запуска
и остановки. Созданный прежним установщиком `/etc/init.d/ptusa_main` удаляется:
его наличие вызывает попытку запуска `systemd-sysv-install`, отсутствующего
на прошивке 2026. Регистрация выполняется через `systemctl enable ptusa_main.service`,
а отключение штатного runtime — через `systemctl disable plcnext.service`.
Unit задаёт порядок после `localbus.service` и взаимное исключение с
`plcnext.service`. Перед изменением прав проверяется остановка процессов
PLCnext, в том числе оставшихся после сбоя службы.
Службы `localbus` и `plcnext-recovery` сохраняются. Использование SysV для
пользовательской программы описано также в
[инструкции Phoenix Contact](https://plcnext.jp/archives/5019).

Установка включает запуск после перезагрузки, но не запускает программу
немедленно и не перезагружает контроллер. На SysV для ручного управления от root:

```sh
/etc/init.d/ptusa_main start
/etc/init.d/ptusa_main status
/etc/init.d/ptusa_main stop
/etc/init.d/ptusa_main restart
tail -f /var/log/ptusa_main.log
```

На systemd используйте команды `ptusastart`, `ptusastop`, `ptusarestart`
либо `sh /opt/ptusamain/setup-ptusa-autostart.sh start|stop|restart|status`.
Напрямую можно использовать `systemctl start|stop|restart|status ptusa_main.service`.
Проверка регистрации без запуска программы:

```sh
systemctl is-enabled ptusa_main.service plcnext.service
systemctl cat ptusa_main.service
```

Ожидаемые состояния автозапуска: `enabled` для `ptusa_main.service` и
`disabled` для `plcnext.service`. До ручного запуска или перезагрузки
`ptusa_main.service` остаётся `inactive`.

Установка проверена на AXC F 2152 с прошивкой `26.0.5.124`: `check` и
`install` выполняются успешно, unit загружен без ошибок и включён в
автозапуск, автозапуск PLCnext отключён. Запуск Ptusa_main и перезагрузка
в эту проверку не входили.

Установка также создаёт команды в `/usr/bin`, который входит в `PATH`
пользователей `admin` и `root` на PLCnext. Их можно вызывать из любого каталога:

| Команда | Действие |
|---------|----------|
| `ptusastart` | Запуск службы |
| `ptusastop` | Остановка службы |
| `ptusarestart` | Перезапуск службы |
| `ptusainstall` | Повторная установка |
| `ptusauninstall` | Удаление службы и созданных команд |

При запуске от `admin` команда запрашивает пароль **root** через `su`.
В root-сеансе пароль повторно не запрашивается. Использовать `sudo` не нужно:
его разрешения на контроллере ограничены. Повторная установка удаляет старые
команды установщика из `/usr/local/bin`; чужие файлы сохраняются.

`ptusainstall` использует `/opt/ptusamain/setup-ptusa-autostart.sh`, если он
есть, чтобы применять обновлённый скрипт из каталога программы.
Иначе используется установленная служба. Повторная установка обновляет
созданные команды; чужие файлы с такими именами не перезаписываются.

Команда `start` по умолчанию разрешает запись DO/AO. Аргументы сохраняются
в `/etc/default/ptusa_main`, начальное значение — `PTUSA_ARGS='main.plua'`.
Если существует `/opt/main/ptusa_main.ini`, служба автоматически подключает
его через `--config`. Стандартное `main.plua` заменяется на запуск через
конфиг, чтобы имя скрипта также читалось из параметра `script` в файле.
Без конфига сохраняется запуск `main.plua`.

Дополнительные консольные параметры из `PTUSA_ARGS` применяются поверх
конфига. Явный `--config` или `-c` выбирает другой файл без добавления
конфига по умолчанию. Например, `PTUSA_ARGS='--config /opt/main/other.ini'`.
Для запуска с чтением задайте
`PTUSA_ARGS='main.plua --read_only_io --opc off'` и запустите службу.
Изменённые аргументы сохраняются при повторной установке. Автоматическое
подключение конфига работает и для существующего `/etc/default/ptusa_main`
после повторной установки обновлённого скрипта службы.

Для удаления службы и возврата автозапуска PLCnext выполните от root:

```sh
sh /opt/ptusamain/setup-ptusa-autostart.sh uninstall
```

Эта команда останавливает ptusa_main, восстанавливает автозапуск PLCnext
и сохраняет проект, настройки и лог. PLCnext немедленно не запускается.
На проверенном контроллере `admin` имеет ограниченный список команд sudo;
для первоначальной установки или обновления скрипта используйте `su`
с паролем root, например:

```sh
su -c 'sh /opt/ptusamain/setup-ptusa-autostart.sh install'
hash -r
ptusastart
```

## main.io.lua и адреса

Формат Lua не меняется. У узла контроллера должны быть модули в физическом
порядке; существующий `sys.io.lua` заполняет типы слов через `init_node_AI`
и `init_node_AO`. IP для локального узла не требуется. Контроллер без локальных
модулей не запускает обмен с Axiobus.

`offset` AI/AO измеряется в 16-битных словах, DI/DO — в битах. Для каждого
модуля учитываются также зарезервированные данные обоих направлений.
Смещения остаются такими же, как для AXL F BK ETH, если состав и порядок
модулей не изменились. К ним не добавляются регистры Modbus 8000/9000
или служебные байты LocalbusData.

Пример: DI16 → AI4 → DI8/DO8 → AO4 → DI16 занимает 11 слов (22 байта).
Начала модулей в словах: 0, 1, 5, 6, 10; в битах: 0, 16, 80, 96, 160.
Клеммы DI8/DO8, расположенные во втором байте слова, получают offset 88.

Драйвер передаёт сырые данные каждого модуля, дополняя нечётную длину до слова
отдельно. Обычные AI/AO используют Big Endian; битовые таблицы и особая
обработка IO-Link и счётчиков сохраняются. Подробный пример генерации
приведён в EasyEPLANner: `docs/developer_manual/plcnext-local-bus.md`.

Для DI8/DO8 `2701916` и `2702071` с длиной PDI 1 байт полезные данные
размещаются во втором байте слова, в битах 8–15 относительно начала модуля.
При чтении сырой байт `A5` становится словом `00 A5`; при записи передаётся
только второй байт слова. Это преобразование общее для LIBRARY и IOCTL.
Например, после DI16 и DO16 входы и выходы DI8/DO8 занимают биты 40–47.
Резервный байт и смещения следующих модулей при этом сохраняются.
Аппаратный образ LIBRARY/IOCTL также выровнен до слова: полезный байт
DI8/DO8 находится по адресу `m_inOffset + 1` / `m_outOffset + 1` в библиотеке
и во втором байте слова модуля в IOCTL. Преобразование выполняется также
в транспорте; одной перестановки байта в таблицах проекта недостаточно.
При команде `5F` образ слота должен быть `00 5F`, а не `5F 00`.

Длина данных берётся из записи идентификации PDI `0x0037` (байты 2–3,
Big Endian) и сохраняется при инициализации. `getProcessDataLength()`
в используемой библиотеке возвращает ноль для обнаруженных DI16/DO16,
поэтому для проверки размеров этот метод не используется. На AXC F 2152
для модулей `2688022` и `2688048` подтверждена длина по 2 байта.
В IOCTL дополнительно сверяются тип, идентификатор и длина из конфигурации
мастера (`Complete_Read_Configuration`) и PDI `0x0037`. Артикул читается
из PDI `0x000A` как десятичная ASCII-строка. Любой неудачный PDI прерывает
сканирование с ошибкой; он не считается концом списка модулей.

В `libAxiobus.so.11.2` поле `AXLModule::m_processDataLength` не
инициализировано корректно. От него зависят также `getInputProcessData()`
и `setOutputProcessData()`: при нулевом поле они не копируют данные,
хотя последующая запись шины сообщает об успехе. На AXC F 2152 это
подтверждено одновременно активной командой IN2M1 в таблице DO и нулевым
буфером выходного модуля. У входных модулей поле может содержать случайное
большое значение, поэтому чтение входов при этом продолжает работать.

Адаптер копирует данные через защищённые указатели `m_inOffset`/
`m_outOffset`, используя проверенный размер PDI. Доступ оформлен
указателями на члены базового класса, без смещений полей в памяти
и без приведения объекта AXLModule к наследнику. Перед копированием
проверяются размер и наличие буферов. Бинарная библиотека и её заголовки
не изменяются; этот обход нужен для чтения и записи на ARM и x64.

## Проверка конфигурации и ошибок

Перед чтением и записью проверяются состояние шины, наличие модулей,
совпадение их артикулов и размеров с потоками AI/AO из Lua, а также равенство
`DI_count = 16 * AI_count`, `DO_count = 16 * AO_count`. Это защищает от записи
по адресам другой конфигурации. Для локальных данных требуется актуальный
`sys.io.lua` с описаниями используемых артикулов.

Допустим один активный узел контроллера с локальными модулями. Ошибки
инициализации, конфигурации, чтения или записи устанавливают ошибку узла и
блокируют последующую запись до успешного чтения. Повторная попытка выполняется
через `delay_time`, без создания сетевого соединения к контроллеру.

IOCTL удерживает SYSFAIL при инициализации и записывает начальный нулевой
образ под этой блокировкой. После проверки Lua-конфигурации, успешного
чтения и заполнения всего выходного образа первая запись снимает SYSFAIL.
Каждой последующей записи требуется новое успешное чтение. Сбой ioctl,
MXI/PDI или диагностики сбрасывает готовность и требует повторного
сканирования. Ошибка проверки Lua также устанавливает SYSFAIL.
При штатном уничтожении драйвера SYSFAIL устанавливается перед закрытием
устройства; поведение при аварийном завершении процесса нужно проверить
отдельно. Параметр `--read_only_io` в IOCTL оставляет SYSFAIL установленным.

### Отображение диагностики

IOCTL `0x5A` возвращает статус, код и место ошибки в Big Endian.
Это порядок аппаратных регистров; поля структуры MXI ioctl используют
порядок байтов процессора. Прямой драйвер преобразует все три регистра.
До исправления байты `02 E0` на ARM/x64 ошибочно читались как `0xE002`,
что давало ложную ошибку I/O и признаки остановленной шины. Верное значение
`0x02E0` означает RUNNING, ACTIVE, BUS_READY и удержание выходов SYSFAIL;
оно допускается до первой проверенной записи выходного образа.

Подробности локальной шины передаются в стандартное поле `description`
списка тревог PAC/EasyServer и в журнал программы. Ошибка обмена содержит
код, место ошибки, расшифровку флагов Axiobus или конкретную причину
отказа: права доступа, инициализация, PDI, отсутствующий модуль,
несовпадение артикулов либо размера данных с `main.io.lua`.
При несовпадении артикулов указываются слот, обнаруженный артикул
и ожидаемые значения AI/AO. При смене причины обновляется идентификатор
списка тревог; повтор одинакового сообщения не создаёт новую запись.

Неудачный обмен сохраняет тревогу `1-1-N` с приоритетом 100 и блокирует
запись до успешного чтения. При работающей шине её диагностические сообщения
показываются отдельной тревогой `7-1-N`: I/O error и ошибка синхронизации —
приоритет 250; предупреждения, SYS_FAIL, FORCE_MODE и запрос параметризации —
приоритет 500. Эти сообщения не меняют существующие условия готовности
библиотечного драйвера и не устанавливают ошибку чтения. IOCTL дополнительно
блокирует обмен при FORCE_MODE, SYNC_FAILED и PARAM_REQUIRED; I/O warning/error
остаются уведомлениями. Узел получает состояние
`DST_WARNING`, которое используется стандартным отображением узлов SCADA.
После исчезновения причины соответствующая тревога снимается автоматически;
при отключении узла для обслуживания её снимает обычная команда NODEENABLED.

Пример сообщения: `status=0x02E2, код=0x3130, param2=0x0004, слот 4`:
ошибка I/O, отсутствующее или неисправное питание I/O, выходные данные
заблокированы SYS_FAIL. `param2` сохраняется также в исходном виде;
для локализованных ошибок это номер слота, начиная с 1.
Расшифровки флагов и типовых кодов соответствуют разделам 2.3 и 3.4
[UM EN AXL F SYS DIAG](https://www.plcnext-community.net/robohelp/security/assets/docs/um_en_axl_f_sys_diag_8663_en_08.pdf).
Неизвестные коды сохраняются в шестнадцатеричном виде. Дополнительные
сообщения устройства из PDI `0x0018` в текущем варианте не опрашиваются:
отображается самая приоритетная диагностика регистров мастера шины.

Тесты `local_bus_io.*` используют подменный драйвер и проверяют адреса,
порядок байтов, выходные данные, несовпадение состава, ошибки и восстановление.
Они не заменяют проверку на реальных AXC F 2152/3152 с установленными модулями.
Тесты `axio_ioctl_test.*` проверяют байтовые кадры MXI/PDI, холодную и активную
шину, нечётные размеры модулей, повреждённые ответы, ошибки транспорта,
SYSFAIL и восстановление. Приведённые далее аппаратные проверки относятся
к LIBRARY, а не к новой реализации IOCTL.

До объединения 12.10.2026 оба транспорта собраны для AXC F 2152
(SDK 2024.0.17 LTS, ARM32) и AXC F 3152 (SDK 2026.0.5 LTS, x86_64).
В ELF-файлах IOCTL
нет `NEEDED libAxiobus.so.11`; библиотечные варианты сохраняют эту зависимость.
После объединения зависимость сохраняется в общей сборке для обоих типов узла.
Все 43 профильных теста прошли в MinGW и CTest/MSVC, включая 14 тестов
нового драйвера. Общий CTest/MSVC завершился с 857 успешными проверками
из 887: 25 тестов `LuaManagerTest` завершились ошибками, 5 дополнительных
целей не были собраны. Это ограничение полного прогона, а не подтверждение
аппаратной работоспособности IOCTL.

Общая сборка с выбором транспорта по `ntype` также собрана для обоих SDK.
Проверка ELF подтвердила наличие обеих реализаций и зависимости
`libAxiobus.so.11`, библиотека скопирована рядом с программой.
Все 48 профильных проверок CTest/MSVC прошли, включая выбор транспорта
по `202/203/204/205`, повторное использование драйвера, запрет записи
до чтения после смены транспорта и запрет двух локальных узлов.
С учётом проверок существующего обмена I/O прошли 94 теста CTest/MSVC.
В EasyEPLANner прошли 257 проверок I/O и межпроектного обмена: новые типы
сохраняются в Lua, используют прежние смещения и распознаются как контроллеры.
После исправления порядка байтов диагностики прошли все 96 проверок
CTest/MSVC, включая реальные последовательности байтов `02 E0 00 00 00 00`
и диагностику с ненулевым кодом и номером слота. Оба ELF собраны повторно.

На AXC F 2152 выполнен 15-секундный запуск с `--read_only_io`: обнаружены
три DI16 `2688022` и два DO16 `2688048`, проверка состава и циклическое
чтение завершились без ошибок узла. Запись DO/AO в этой проверке отключена;
её необходимо проверять отдельно. Для AXC F 3152 проверена сборка с SDK.

После исправления копирования 12.10.2026 на AXC F 2152 проверена запись:
команда IN2M1 (`DO offset=49`) присутствует в таблице DO, буфере модуля
слота 4 и последнем успешно записанном буфере Axiobus. При активных
выходах 48, 49, 50, 56 данные слота 4 равны `07 01`; общий буфер шины
равен `00 00 00 00 00 00 07 01 00 00`. Три последовательных снимка
подтвердили статус `0x00E0` без ошибок, несмотря на оставшуюся нулевую
длину внутри библиотеки. Проверка выполнена чтением памяти работающего
процесса и аппаратной диагностики, без повторной инициализации Axiobus.
Электрическое измерение выходов в эту проверку не входит.
