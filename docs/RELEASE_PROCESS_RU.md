# Порядок выпуска релизов

Англоязычная версия: [RELEASE_PROCESS.md](RELEASE_PROCESS.md).

Один строковый номер версии и одна команда на публикацию.
Это руководство описывает, как релизы `ptusa_main` собираются
средствами `CI`; правила именования тегов находятся в
[CONTRIBUTING.md](CONTRIBUTING.md#versioning-and-tags)
(на английском языке).

## Источник версии

Версия проекта — четырёхкомпонентная CalVer-строка в
`CMakeLists.txt`:

```cmake
project(ptusa_main VERSION YYYY.MM.DD.N)
```

Она добавляется в binaries через `version_info.h` (вывод
`-v`, сведения сервера `OPC UA`, версия в ресурсе `Windows`),
поэтому тег релиза обязан совпадать с ней побайтово — без
префикса `v` и без суффиксов. Релиз, у которого тег отличается
от строки `CMake`, отклоняется `CI` (см. ниже).

## Выпуск релиза

1. Откройте запрос на внесение изменений (`pull request`),
   меняющий `project(ptusa_main VERSION ...)` в `CMakeLists.txt`,
   и смержите его в `master`. Сам мерж и есть решение о релизе.
2. Проверьте черновик. Задача `autocut-release` из `cmake.yml`
   следит за фиксациями в master-ветви и, если для версии из
   `CMake` ещё нет релиза, создаёт черновик с этим именем,
   нацеленный на мерж-коммит. При публикации `GitHub` создаст
   тег ровно из этого коммита; в тело черновика автоматически
   подставляются сгенерированные заметки — список pull request'ов,
   зафиксированных с прошлого релиза.
3. Опубликуйте. Нажмите `Publish` (или `gh release edit
   <version> --draft=false`). Это запускает `on: release` в
   `cmake.yml`: `workflow` выполняется из коммита тега,
   проверяет версию, строит полную матрицу, а
   `publish-release` добавляет все архивы к релизу.

Никакого ручного `gh release create`, никакого ручного
управления тегами и changelog'ами.

## Что гарантирует CI

- Метка версии (`version_ok` в детекторе изменений) сверяет тег
  со `project(... VERSION ...)`, разобранной из коммита тега.
  При несовпадении сборка завершается неудачно, матрица
  пропускается, а релиз остаётся без ассетов.
- `publish-release` выполняется только на событии `release` и
  только после полностью успешной матрицы; загрузка идёт через
  `gh release upload --clobber`, поэтому перезапуски
  идемпотентны.
- Право `contents: write` выдано только этим двум задачам.

## Использование

- Архивы: `Windows-MSVC.7z`, `Windows-MinGW.7z`, `Linux.7z` и
  кросс-сборки PLCnext `Linux-AXCF2152-*`, `Linux-AXCF3152-*`,
  `Linux-AXCF2000-*` — собираются из коммита тега, поэтому
  binaries всегда соответствуют тегу.
- Пересобрать ассеты: перезапустите упавший release-прогон.
  Учтите, что прогон использует workflow-файл из коммита тега;
  исправления, принятые в `master` позже, на уже выпущенный тег
  не влияют — в этом случае загрузите ассеты вручную из
  артефактов прогона.
- Пересоздать заметки (для черновика): `gh release edit
  <version> --generate-notes`.
- Исправления в тот же день: поднимите ревизию `.N` и повторите
  процедуру.
- При удалении релиза его тег остаётся. Следующий пуш в master
  снова создаст черновик этой версии на существующий тег. Чтобы
  полностью вывести версию, удалите и релиз, и тег,
  либо двигайтесь дальше через фиксацию новой версии.
