# Порядок выпуска релизов

[English version](RELEASE_PROCESS.md)

Один строковый номер версии и одна команда на публикацию.
Например: номер `2026.11.18.0`, публикация -
`gh release edit 2026.11.18.0 --draft=false`.
Это руководство описывает, как релизы `ptusa_main` собираются
средствами `CI`;
[правила именования тегов](CONTRIBUTING.md#versioning-and-tags)
находятся в `CONTRIBUTING.md` (документ на английском языке).

## Источник версии

Версия проекта — четырёхкомпонентный номер формата
`ГГГГ.ММ.ДД.Н` (CalVer) в `CMakeLists.txt`:

```cmake
project(ptusa_main VERSION YYYY.MM.DD.N)
# например: project(ptusa_main VERSION 2026.11.18.0)
```

Последняя компонента - порядковый номер выпуска
в пределах дня: `0` для первого релиза дня,
затем `1`, `2` и далее - повторные выпуски
того же дня (hotfix).

Номер версии добавляется в исполняемые файлы (`binaries`) в
виде строки через `version_info.h` (вывод `-v`, сведения
сервера `OPC UA`, версия в ресурсе `Windows`), поэтому тег
релиза обязан совпадать с номером версии побайтово — без
префикса `v` и без суффиксов. Релиз, у которого тег отличается
от строки `CMake`, отклоняется `CI`
([см. ниже](#что-гарантирует-ci)).

## Выпуск релиза

1. Откройте запрос на внесение изменений (`pull request`),
   меняющий `project(ptusa_main VERSION ...)` в
   `CMakeLists.txt`, и объедините его с веткой `master`
   (операция merge). Само объединение (merge) и есть решение
   о релизе.
2. Проверьте черновик релиза (draft). Задача `autocut-release`
   из `cmake.yml` следит за фиксациями в master-ветви (push)
   и, если для версии из `CMake` ещё нет релиза, создаёт
   черновик с этим именем, нацеленный на коммит объединения
   (merge commit). При публикации `GitHub` создаст тег ровно
   из этого коммита; в тело черновика автоматически
   подставляются примечания к релизу (release notes) — список
   pull request'ов, зафиксированных с прошлого релиза.
3. Опубликуйте. Нажмите «Опубликовать» (`Publish`) или выполните
   `gh release edit <version> --draft=false`. Это запускает
   `on: release` в `cmake.yml`: файл конвейера (`workflow`)
   выполняется из коммита тега, проверяет версию, строит
   полную матрицу сборок, а `publish-release` добавляет все
   архивы к релизу.

Не использовать ручной `gh release create`, ручное управление
тегами и ручное управление changelog'ами.

## Что гарантирует CI

- Метка версии (`version_ok` в детекторе изменений) сверяет тег
  со `project(... VERSION ...)`, разобранной из коммита тега.
  При несовпадении сборка завершается неудачно, матрица
  пропускается, а релиз остаётся без вложений (assets).
- `publish-release` выполняется только на событии `release` и
  только после полностью успешной матрицы; загрузка идёт через
  `gh release upload --clobber`, поэтому перезапуски
  идемпотентны.
- Право `contents: write` выдано только этим двум задачам.

## Использование

- Архивы: `Windows-MSVC.7z`, `Windows-MinGW.7z`, `Linux.7z` и
  кросс-сборки PLCnext `Linux-AXCF2152-*`, `Linux-AXCF3152-*`,
  `Linux-AXCF2000-*` — собираются из коммита тега, поэтому
  исполняемые файлы всегда соответствуют тегу.
- Пересобрать вложения релиза (assets): перезапустите упавший
  прогон публикации релиза. Учтите, что прогон использует файл
  конвейера из коммита тега; исправления, принятые в `master`
  позже, на уже выпущенный тег не влияют — в этом случае
  загрузите вложения вручную из артефактов сборки
  (build artifacts) прогона.
- Пересоздать примечания к релизу (release notes) для
  черновика: `gh release edit <version> --generate-notes`.
- Исправления в тот же день: поднимите ревизию `.N` и повторите
  процедуру.
- При удалении релиза тег остаётся. Следующая фиксация (push)
  в `master` снова создаст черновик этой версии на
  существующий тег. Чтобы полностью вывести версию, удалите и
  релиз, и тег, либо двигайтесь дальше через фиксацию новой
  версии.
